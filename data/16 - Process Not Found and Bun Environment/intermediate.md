1. What are the key differences, runtime behaviors, and portability tradeoffs between using `process.env` and `Bun.env`?

**Deep explanation:** Both `process.env` and `Bun.env` provide access to environment variables, but they carry distinct implications for cross-runtime portability and system architecture:
- **`process.env` (Maximum Portability):** `process.env` is the universal, industry-standard convention across Node.js, Express, serverless runtimes (AWS Lambda, Google Cloud Functions), Docker containers, and frontend bundlers (Vite, Next.js). In Bun, `process.env` is implemented as an alias and compatibility proxy over Bun's internal environment storage. Pairing `process.env` with `@types/node` ensures that code remains 100% portable—the exact same application can run on Node.js, Bun, or edge runtimes without modification.
- **`Bun.env` (Bun-Native Global):** `Bun.env` is Bun's native API for reading environment variables. It directly exposes Bun's internal string-to-string hash map without going through Node compatibility proxies, offering a slightly simpler, idiomatic interface for Bun projects. However, referencing `Bun.env` creates vendor lock-in: the code will immediately throw a `ReferenceError: Bun is not defined` if executed in Node.js or standard browser environments without polyfills or build steps.
- **Trade-off Summary:** Use `process.env` + `@types/node` when authoring shared libraries, migrating existing Node/Express codebases, or targeting multiple runtime environments. Use `Bun.env` when writing greenfield microservices, scripts, or internal tooling that are explicitly designed to leverage the Bun ecosystem exclusively.

**Interview answer:** "`process.env` offers universal portability across Node.js, Bun, and container runtimes, making it the preferred approach for cross-platform codebases when paired with `@types/node`. `Bun.env` is Bun's native, zero-overhead environment global, but it locks the codebase to the Bun runtime and breaks compatibility if run directly under Node.js."
