1. Why does TypeScript report the error "Cannot find name 'process'" in a Bun project even though `process.env` works at runtime, and how do ambient declaration packages resolve this?

**Deep explanation:** Bun is engineered as a high-performance, drop-in replacement for Node.js. It natively implements Node.js runtime globals—including `process`—directly in its Zig/C++ core. As a result, when code using `process.env` is executed via `bun run`, it runs without runtime exceptions. However, TypeScript's static type checker runs independently of the JavaScript runtime and relies exclusively on ambient declaration files (`.d.ts`) to understand what global symbols exist. 

By default, standard ECMAScript library definitions (e.g., `esnext`, `dom`) do not define `process` because it is a platform-specific host object rather than an ECMAScript standard global. To resolve this diagnostic error:
- **Install `@types/node`:** Running `bun add -d @types/node` downloads Node's official ambient typings into `node_modules/@types/node`. This file exposes `declare var process: NodeJS.Process`, providing full type information for `process`, `process.env`, and associated Node APIs.
- **Restart TS Server:** IDE language clients (such as VS Code's TypeScript Language Server) maintain an in-memory cache of resolved module and declaration graphs. After installing new ambient packages, the IDE may continue displaying cached diagnostic errors until you trigger `TypeScript: Restart TS Server` via the Command Palette (`Ctrl + Shift + P` or `Cmd + Shift + P`), which forces the language server to re-scan `node_modules/@types` and clear the error.

**Interview answer:** "TypeScript flags 'Cannot find name process' because static type checking relies on ambient declaration packages rather than the runtime engine. Installing `@types/node` registers the global `process` type definition, and restarting the IDE's TypeScript language server forces it to re-index the declarations and clear the diagnostic error."
