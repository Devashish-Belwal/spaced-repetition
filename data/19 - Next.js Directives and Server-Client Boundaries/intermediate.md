1. What does the `'use server'` directive do, and what are the critical security and architecture concerns when implementing Server Actions?

**Deep explanation:** The `'use server'` directive is not the syntactic opposite of `'use client'`; it does not turn a component into a React Server Component (all components in the App Router are Server Components by default). Instead, `'use server'` marks an asynchronous function—or an entire file of async functions—as a **Server Action**.
- **RPC Mechanics:** When Next.js compiles a function with `'use server'`, it automatically creates an exposed Remote Procedure Call (RPC) endpoint. Next.js assigns each Server Action a unique, cryptographically hashed endpoint ID and maps incoming HTTP POST requests containing serialized arguments directly to that server-side function. Server Actions can be invoked directly from client event handlers, form `action` attributes, or custom hooks.
- **Security Implications:** Because Server Actions are compiled into public HTTP POST endpoints, they must be treated with the same defensive rigor as public REST or GraphQL APIs:
  1. **Authentication & Authorization:** Never assume a Server Action is secure because its trigger button is hidden behind client-side conditionals. Every Server Action must independently extract and verify the user's session or auth token before executing business logic.
  2. **Strict Input Validation:** Arguments supplied from the browser across the RPC boundary are untrusted. Always validate and sanitize all inputs using runtime schema validation libraries (such as Zod or Valibot) before passing them to databases or internal services.
  3. **Closure and Data Leakage:** Server Actions declared inside Server Components inherit variables from the component scope. If not carefully managed, sensitive server state might inadvertently be serialized into encrypted action closures or exposed in error messages.
  4. **CSRF & Transport Security:** Next.js provides built-in CSRF defenses by comparing the request's `Host` and `Origin` headers for Server Action POST dispatches, but sensitive operations should still enforce re-authentication and rate limiting.

**Interview answer:** "`'use server'` defines a Server Action, exposing an async function as a callable RPC HTTP POST endpoint that executes exclusively on the server. Because Server Actions are public network endpoints accessible to anyone, developers must enforce strict authentication, authorization, and input validation schemas inside every action rather than relying on client UI gates."

2. Why are the `server-only` and `client-only` packages necessary, and how do they enforce build-time module isolation?

**Deep explanation:** In full-stack frameworks like Next.js where server and client code reside in the same project, accidental leakage of server-side code into client bundles is a major security and stability risk.
- **The "Poisoning" Problem:** A developer might write a database client, token generator, or utility that references private server environment variables (e.g., `process.env.DATABASE_URL` or `process.env.STRIPE_SECRET_KEY`). If a Client Component (or another utility imported by a Client Component) imports this file, the build bundler (Turbopack/Webpack) attempts to include it in the browser bundle. This can either fail at build time due to missing Node.js native modules (`fs`, `crypto`, `net`) or, worse, succeed while replacing secret environment variables with `undefined` or exposing private business logic to client inspection.
- **`server-only` Enforcement:** By adding `import 'server-only'` at the top of a server-side module, developers introduce a build-time guard. If any module inside a `'use client'` dependency tree attempts to import that file, Next.js aborts compilation immediately with an explicit error stating that the module cannot be imported from a Client Component.
- **`client-only` Enforcement:** Conversely, `import 'client-only'` guarantees that client modules relying on browser-exclusive APIs (such as `window`, `document`, canvas, or `navigator`) cannot be evaluated in the Node.js or Edge runtime during Server Component rendering or SSR, preventing server execution crashes before deployment.

**Interview answer:** "Boundary packages like `server-only` and `client-only` provide build-time safety guards that prevent unintended cross-environment module imports. Adding `import 'server-only'` forces the compiler to fail immediately if a file containing database connections or secret keys is ever imported into a client bundle, eliminating accidental security leaks."
