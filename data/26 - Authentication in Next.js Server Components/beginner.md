1. Why are React Server Components (RSCs) fundamentally superior to traditional Single-Page Application (SPA) architectures for checking authentication and verifying user sessions?

**Deep explanation:** In traditional client-side Single-Page Applications (e.g., standard Vite or Create React App applications), the browser downloads a blank HTML shell and a JavaScript bundle before execution begins. Authentication checks must occur client-side: the application mounts, reads a token from `localStorage` or memory, or initiates an asynchronous network request (such as `fetch('/api/me')`) to inspect the user's session status. This architecture introduces severe security vulnerabilities and suboptimal user experiences:
- **Flash of Unauthenticated Content (FOUC):** Because the initial UI renders before the asynchronous authentication check resolves, users either see a jarring loading skeleton or experience a brief flash of unauthenticated/unauthorized UI before client-side JavaScript redirects them to `/login`.
- **Client-Side Token Exposure:** Storing tokens in client-accessible storage like `localStorage` or `sessionStorage` exposes credentials to Cross-Site Scripting (XSS) attacks. Even when using cookies, client-side auth waterfalls delay page rendering.
- **Data & Logic Leakage:** When conditional authorization checks happen on the client, the underlying JavaScript containing private route structures, internal API endpoints, and sensitive business logic is included in the client bundle and easily inspected in browser developer tools.

In contrast, Next.js Server Components execute exclusively on the server before any HTML or serialized component tree reaches the browser. A Server Component can inspect incoming HTTP request headers and cookies, query the session store or database directly, and determine authorization status during server rendering:
- **Zero Client Bundle Overhead:** Authentication logic, validation libraries (such as `jsonwebtoken`, `jose`, or `bcrypt`), and database clients never get sent to the browser.
- **Zero FOUC:** The page is rendered in its final, verified state on the server. The user receives complete, authenticated HTML or a clean server-level HTTP redirect—eliminating intermediate loading flickers or unauthorized UI flashes.
- **Immediate Server-Side Abort:** If a user lacks permission, the Server Component invokes `redirect('/login')` or `notFound()`, halting component rendering immediately so unauthorized data is never serialized into the RSC payload or streamed to the client.

**Interview answer:** "React Server Components execute entirely on the server, allowing us to inspect cookies, query the database, and verify sessions before generating any markup. This eliminates client-side network waterfalls and the Flash of Unauthenticated Content (FOUC), while guaranteeing that sensitive auth tokens, business logic, and unauthorized data are never exposed to the client bundle."
