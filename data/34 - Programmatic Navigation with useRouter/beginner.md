1. When should you use `useRouter` from `next/navigation` over the declarative `<Link>` component in Next.js App Router, and what are the architectural trade-offs?

**Deep explanation:** In Next.js App Router, navigating between routes can be accomplished either declaratively via `<Link>` or programmatically using the `useRouter` hook. Choosing the correct approach depends on whether navigation is a direct user intention or the result of an imperative workflow.
- **Declarative Navigation with `<Link>` (Default Standard):** The `<Link>` component should always be your default choice for standard UI links (navigation bars, lists, cards, breadcrumbs). It renders a semantic, accessible HTML `<a>` tag that supports native browser features like right-click ("Open link in new tab"), `Ctrl/Cmd + click`, browser history previews, and search engine crawler indexing (SEO). Furthermore, `<Link>` automatically initializes an `IntersectionObserver` to prefetch the destination route's React Server Component (RSC) payload as soon as the link enters the viewport in production.
- **Programmatic Navigation with `useRouter`:** The `useRouter` hook (imported strictly from `next/navigation` in Client Components marked with `'use client'`) is designed for imperative navigation triggered after logic execution. Key use cases include:
  1. Redirecting users after completing form validation, checkout flows, or Server Actions / API calls.
  2. Executing imperative client-side side effects prior to navigation (e.g., dispatching analytics tracking events, writing to `sessionStorage`, or clearing client state).
  3. Conditional transitions driven by timers, external WebSockets, or multi-step wizard state machines.
- **Architectural Shift in App Router vs. Pages Router:** In the legacy Pages Router (`next/router`), `useRouter` was an omniscient singleton that held both navigation methods (`push`, `replace`) and route state properties (`pathname`, `query`, `asPath`). In the App Router (`next/navigation`), `useRouter` has been decoupled strictly to navigation actions: `push()`, `replace()`, `refresh()`, `back()`, `forward()`, and `prefetch()`. Reading route state is now delegated to specialized hooks like `usePathname()` and `useSearchParams()`.
- **Trade-offs:** Attaching `router.push()` to a `<button>` or `<div>` strips away semantic link functionality: search engine spiders cannot crawl it, screen readers lose navigation semantics, and users cannot middle-click or open the link in a new tab. Programmatic navigation should only be applied when imperative operations must precede the route change.

**Interview answer:** "Use `<Link>` by default for declarative routing to preserve semantic accessibility, SEO discoverability, and automatic viewport prefetching. Reserve `useRouter` from `next/navigation` for programmatic transitions triggered imperatively—such as after validating forms, dispatching analytics, or awaiting mutation results inside Client Components."
