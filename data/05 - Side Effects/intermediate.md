1. How should developers decide whether a side effect belongs inside an event handler versus a `useEffect` hook?

**Deep explanation:** The decision of where to place a side effect is dictated by *causality*—specifically, identifying what triggered the effect:
- **User Interactions -> Event Handlers:** If an effect is the direct consequence of a specific user action (such as clicking a button, submitting a form, or typing into an input), it belongs inside an event handler. Examples include sending a `POST` request on a button click, showing an alert, or navigating to another page. Handling these in event handlers preserves intent, avoids redundant state flags, and ensures the effect executes exactly once per interaction.
- **Rendering & Synchronization -> `useEffect`:** If an effect must run *because the component was displayed on screen* or needs to stay synchronized with external systems as props or state change—regardless of what specific interaction triggered the re-render—it belongs in `useEffect`. Examples include subscribing to a WebSocket chat room when `roomId` changes, registering global window listeners, synchronizing document title, or logging analytics on view impressions.
- **Anti-Pattern Warning:** A frequent mistake is splitting user-driven logic by setting a state variable in an event handler (e.g., `setIsSubmitted(true)`) and placing the resulting network call inside a `useEffect`. This couples unrelated render cycles, adds latency, and creates unnecessary re-render passes.

**Interview answer:** "The decision is guided by causality: if the effect is triggered by a specific user interaction like a click or form submission, it belongs in an event handler; if it is required to synchronize the component with an external system or runs because the component was displayed, it belongs in `useEffect`."
