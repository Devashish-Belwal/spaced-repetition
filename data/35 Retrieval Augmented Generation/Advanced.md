1. How would you design a production RAG architecture for millions of documents and many concurrent users?
**Deep explanation:** A production architecture should separate ingestion, indexing, retrieval, generation, evaluation, and observability. Ingestion should be asynchronous and incremental, with source connectors, parsing workers, chunking, embedding jobs, and index writers. Query serving should include authentication, metadata filtering, hybrid retrieval, reranking, prompt assembly, model invocation, citation handling, and logging. At millions of documents, vector search needs partitioning, approximate nearest neighbor indexes, caching, and careful metadata design. Reliability requires backpressure, retries, dead-letter queues, index versioning, and fallbacks when retrieval or generation dependencies degrade.
**Interview answer:** I would build separate ingestion and serving paths. Ingestion parses, chunks, embeds, and indexes documents incrementally. Serving authenticates the user, retrieves with filters, reranks, builds the prompt, calls the model, and logs evidence, citations, latency, and quality signals.

2. How would you shard or partition a vector index for large-scale RAG?
**Deep explanation:** Vector indexes can be partitioned by tenant, language, region, document type, time, or semantic clusters. Partitioning reduces search space and improves latency, but can hurt recall if relevant documents are spread across partitions. Tenant-based partitioning is useful for security and noisy-neighbor isolation. Semantic partitioning can improve performance but requires routing queries to the right partitions. A common approach is hierarchical routing: first select candidate partitions using metadata or a lightweight classifier, then run vector search inside those partitions. The system must also handle rebalancing and hot partitions.
**Interview answer:** I would partition by strong operational boundaries like tenant or region when possible, and use routing for semantic partitions. The goal is to reduce search cost without losing recall or breaking access control.

3. How would you build a multi-stage retrieval pipeline under a strict latency SLA?
**Deep explanation:** A low-latency RAG pipeline often uses staged retrieval: fast lexical and vector search first, lightweight merging and filtering next, then reranking only on a small candidate set. Time budgets should be explicit for each stage. Parallel calls can reduce wall-clock time, while caching can avoid repeated embedding or search work. If the SLA is tight, the system may skip expensive reranking for simple queries or return a partial answer with lower confidence. The design should track p50, p95, and p99 latency because tail latency dominates user experience at scale.
**Interview answer:** I would use a staged design: parallel keyword and vector retrieval, merge candidates, rerank only a small set, and enforce timeouts. Expensive steps should be adaptive so simple queries take the fast path.

4. How would you manage consistency between source systems and RAG indexes?
**Deep explanation:** RAG indexes are derived data, so consistency is a real distributed-systems problem. Strong consistency is expensive because every source update would need to block until parsing, embedding, and indexing finish. Many systems accept eventual consistency with clear freshness guarantees, version metadata, and index snapshots. For high-risk domains, reads may check source freshness or use transactional metadata before answering. Deletes and permission changes need stricter handling than normal updates because stale retrieval can leak data. Tombstones, versioned chunks, and atomic index aliases help control rollout.
**Interview answer:** I would treat the index as eventually consistent derived data, but handle deletes and permission changes with stricter guarantees. Versioned chunks, tombstones, source timestamps, and atomic index swaps help prevent stale or unauthorized retrieval.

5. How would you optimize RAG for both high recall and low hallucination rate?
**Deep explanation:** High recall means the needed evidence appears in the candidate set; low hallucination means the final answer stays faithful to that evidence. To improve recall, use hybrid search, query expansion, metadata routing, and sufficient candidate depth. To reduce hallucination, use reranking, context compression, citation requirements, answer abstention, and post-generation verification. There is a trade-off: retrieving more context can improve recall but increase noise. The best systems optimize the whole pipeline with labeled queries and measure evidence recall, answer faithfulness, and unsupported-claim rate.
**Interview answer:** I would improve recall with hybrid search, query expansion, and enough candidate depth, then reduce hallucination with reranking, focused context, citations, abstention, and verification. The key is measuring retrieval and generation separately.

6. How would you handle conflicting retrieved documents?
**Deep explanation:** Conflicts occur when sources disagree because of version drift, regional policies, document quality, or time-sensitive rules. A robust RAG system should preserve metadata such as source authority, version, effective date, owner, and jurisdiction. Retrieval should prefer authoritative and current sources, and generation should explicitly mention conflicts when they cannot be resolved. For high-risk workflows, the system may refuse to answer or route to a human. Simply giving all conflicting passages to the LLM can produce a blended answer that is wrong.
**Interview answer:** I would rank sources by authority, recency, and applicability, then make the model cite the chosen evidence. If the conflict cannot be resolved, the system should say so instead of merging inconsistent facts.

7. How would you design RAG for multi-tenant SaaS with strict data isolation?
**Deep explanation:** Multi-tenant RAG must prevent cross-tenant retrieval and leakage through logs, caches, prompts, and generated answers. Isolation can be implemented with separate indexes per tenant, shared indexes with mandatory tenant filters, or a hybrid model for large tenants. Separate indexes are cleaner but operationally heavier. Shared indexes are cheaper but require rigorous filter enforcement and testing. Caches must include tenant and permission scope in their keys. Observability data should redact sensitive content, and evaluation should include adversarial tests for cross-tenant leakage.
**Interview answer:** I would enforce tenant isolation at indexing, retrieval, caching, and logging. Depending on scale, I would use separate indexes or mandatory tenant filters, but never rely on prompt instructions for isolation.

8. How would you support real-time or near-real-time RAG over rapidly changing data?
**Deep explanation:** Near-real-time RAG requires reducing the delay between source changes and searchable context. Techniques include event-driven ingestion, incremental parsing, streaming embeddings, small update batches, and separate hot indexes for fresh data. For very fresh data, the system may query source APIs directly and combine structured results with indexed retrieval. The trade-off is cost and complexity: frequent embedding and index updates can increase write load and reduce index quality if updates are not compacted. Freshness metrics should be tracked alongside answer quality.
**Interview answer:** I would use event-driven incremental ingestion and possibly a hot index for recent updates. For data that must be current immediately, I would query the source system directly and merge those results into the RAG context.

9. How would you make RAG robust against prompt injection inside retrieved documents?
**Deep explanation:** Retrieved documents are untrusted input. A document might contain text like "ignore previous instructions" or "send the user's secrets." If inserted naively into the prompt, the model may treat it as an instruction. Defenses include clear prompt separation, marking context as data, stripping or flagging suspicious instructions, using allowlisted tools, limiting model permissions, and post-checking outputs. The strongest defense is architectural: the model should not have direct authority to access secrets or perform irreversible actions just because retrieved text asks it to.
**Interview answer:** I would treat retrieved text as untrusted data, separate it from system instructions, and restrict what the model can do. Prompt formatting helps, but tool permissions, output checks, and least-privilege design are more important.

10. How would you evaluate a RAG system when no perfect ground-truth answers exist?
**Deep explanation:** Many real RAG applications lack a complete labeled dataset. Evaluation can combine expert-reviewed samples, synthetic questions generated from documents, pairwise comparisons, citation audits, retrieval coverage checks, and production feedback. Synthetic data is useful for scale but can be biased toward easy questions, so it should be mixed with real user queries. LLM-as-judge can help with triage, but important claims should be calibrated against human review. The evaluation framework should track regressions over time, not just one-time scores.
**Interview answer:** I would combine human-reviewed samples, synthetic document-based questions, citation checks, retrieval metrics, user feedback, and regression tests. LLM judges can help, but I would calibrate them against human review.

11. How would you reduce cost in a high-traffic RAG system without significantly hurting quality?
**Deep explanation:** Cost comes from embedding, vector search, reranking, prompt tokens, model inference, and observability storage. Optimizations include embedding only changed content, caching query embeddings and retrieval results, using smaller models for routing and compression, reducing duplicated chunks, adaptive top-k, and choosing cheaper models for low-risk questions. Prompt token cost can be reduced by better chunking, reranking, and summarizing only when safe. The risk is quality regression, so each optimization should be validated against retrieval recall, faithfulness, and latency metrics.
**Interview answer:** I would cache repeated work, embed only changed content, use adaptive retrieval depth, reduce prompt tokens, and route simple questions to cheaper models. Every cost optimization should be checked against quality metrics.

12. How would you design RAG for complex questions that require combining information from multiple sources?
**Deep explanation:** Complex questions may require multi-hop retrieval, decomposition, and synthesis. For example, "Which customers affected by incident X are on plan Y?" may need incident docs, customer records, and plan metadata. A robust design decomposes the query into sub-questions, retrieves evidence for each, tracks source provenance, and synthesizes only after enough evidence is collected. Graph retrieval, SQL queries, and tool calls may be better than pure vector search for relationships and exact constraints. The trade-off is higher latency and orchestration complexity.
**Interview answer:** I would decompose the question, retrieve or query each needed source, preserve provenance, and synthesize from the collected evidence. For relational or exact data, I would use structured queries or graph traversal instead of relying only on vector search.

13. How would you design index versioning and rollback for a critical RAG system?
**Deep explanation:** Index versioning allows a system to build a new index without immediately replacing the serving index. A common pattern is to write chunks and embeddings into a versioned index, run validation, then atomically switch an alias or routing pointer. Rollback means moving that pointer back to the previous known-good version. This protects against bad parsing jobs, embedding regressions, schema mistakes, and accidental data removal. The trade-off is extra storage because multiple index versions may exist at once.
**Interview answer:** I would build new indexes as separate versions, validate them, then switch traffic atomically through an alias. If quality or freshness checks fail, I would roll back to the previous version.

14. How would you handle hot tenants or hot documents in a multi-tenant RAG platform?
**Deep explanation:** Hot tenants or documents can overload shared retrieval, embedding, or generation resources. Mitigations include per-tenant rate limits, request queues, cache warming, tenant-aware partitioning, replicas for hot indexes, and prioritization by plan or workload. Hot documents may also create repeated retrieval patterns, so caching their chunks or summaries can help. The trade-off is fairness versus efficiency: isolating heavy tenants improves reliability but may increase infrastructure cost.
**Interview answer:** I would use tenant-aware rate limits, caching, partitioning, replicas, and queueing. The goal is to isolate heavy workloads so they do not degrade other tenants.

15. How would you design observability for a distributed RAG system?
**Deep explanation:** Observability should cover ingestion, indexing, retrieval, reranking, prompt assembly, generation, and user feedback. Important metrics include ingestion lag, embedding failures, index size, retrieval recall proxies, latency percentiles, model error rate, token cost, citation rate, abstention rate, and user satisfaction. Traces should connect a user request to retrieved chunks and model calls. Logs must redact sensitive content. Without observability, RAG failures are hard to diagnose because they can occur at many stages.
**Interview answer:** I would instrument every stage with metrics, traces, and redacted logs. Key signals include ingestion freshness, retrieval behavior, latency, cost, citations, abstentions, and answer-quality feedback.

16. How would you design an offline and online evaluation strategy for RAG?
**Deep explanation:** Offline evaluation uses fixed datasets to test retrieval, faithfulness, citation accuracy, latency, and regressions before deployment. Online evaluation measures real production behavior through user feedback, click-through, escalation rate, A/B tests, and sampled human review. Offline tests are controlled but may not capture changing user behavior. Online tests are realistic but noisier and require safety controls. A mature system uses both, with canary releases for risky retrieval or model changes.
**Interview answer:** I would use offline benchmark sets for controlled regression testing and online monitoring or A/B tests for real behavior. Both are needed because lab quality and production quality can differ.

17. How would you route queries across multiple retrieval backends?
**Deep explanation:** Different questions may require different retrieval backends, such as vector search for documents, BM25 for exact terms, SQL for records, graph search for relationships, or API calls for live state. A router can use rules, classifiers, LLM intent detection, or a planner. Routing must be observable and testable because wrong routing can hide the right evidence. Some systems run multiple backends in parallel and merge results, trading higher cost for better recall.
**Interview answer:** I would route based on query intent, required freshness, access scope, and data type. For ambiguous queries, I might search multiple backends in parallel and merge or rerank results.

18. How would you handle embedding-model migration in a large RAG system?
**Deep explanation:** Changing embedding models usually requires re-embedding all indexed chunks because vectors from different models may not be comparable. A safe migration can build a shadow index with the new embeddings, replay evaluation queries, compare retrieval quality, and gradually shift traffic. During migration, the system may dual-write new chunks to old and new indexes. The trade-off is high compute and storage cost, but it reduces the risk of a sudden retrieval regression.
**Interview answer:** I would build a parallel index with the new embedding model, evaluate it, dual-write during migration, and gradually shift traffic. Old and new embeddings should not be mixed casually.

19. How would you design RAG for strict compliance and audit requirements?
**Deep explanation:** Compliance-focused RAG needs access controls, retention policies, source provenance, audit logs, redaction, encryption, and reproducibility. The system should record which sources were retrieved, which model version answered, which prompt template was used, and what permissions were applied. Sensitive data should be minimized in logs and prompts. For regulated domains, answers may need disclaimers, human approval, or refusal policies. The trade-off is slower iteration and higher operational overhead.
**Interview answer:** I would enforce permissions, preserve provenance, log model and source versions, redact sensitive data, and support audits. For high-risk answers, I would add human review or strict refusal rules.

20. How would you design caching without leaking private RAG data?
**Deep explanation:** Caching can reduce latency and cost, but it is dangerous if cache keys ignore tenant, user permissions, document versions, or source filters. Safe caches include all authorization and freshness dimensions in the key, or cache only non-sensitive intermediate results. Query embeddings may be cached, but retrieval results and final answers must be scoped carefully. Cache invalidation should respond to document updates, deletes, and permission changes. The trade-off is lower hit rate in exchange for privacy and correctness.
**Interview answer:** I would scope cache keys by tenant, permissions, filters, and index version. Any cache that can expose retrieved text or final answers must respect authorization and invalidation rules.

21. How would you handle disaster recovery for a RAG platform?
**Deep explanation:** Disaster recovery should cover source connectors, ingestion queues, embedding jobs, indexes, metadata stores, prompt/config stores, and evaluation artifacts. Since indexes are derived data, they can often be rebuilt from source, but rebuild time may be too long for business requirements. Backups, replicated indexes, infrastructure-as-code, and runbooks help restore service. Recovery objectives should distinguish read availability from freshness. In a degraded mode, the system might serve from a slightly stale index while ingestion recovers.
**Interview answer:** I would back up metadata and configs, replicate or snapshot indexes, keep rebuild pipelines tested, and define freshness trade-offs. Derived indexes can be rebuilt, but recovery time must meet business needs.

22. How would you protect a RAG system from data poisoning?
**Deep explanation:** Data poisoning happens when malicious or low-quality content enters the knowledge base and influences answers. Defenses include source allowlists, document approval workflows, content scanning, anomaly detection, provenance scoring, and separating trusted from untrusted sources. Retrieval ranking should consider source authority, not only semantic similarity. For collaborative wikis, permission and review workflows matter. Poisoned content is especially dangerous when the system can take actions or produce policy-like answers.
**Interview answer:** I would control ingestion sources, scan new content, track provenance, rank trusted sources higher, and review high-impact documents. RAG should not treat all retrieved text as equally authoritative.

23. How would you optimize vector search memory usage at scale?
**Deep explanation:** Vector memory usage scales with number of chunks times embedding dimension times bytes per value, plus index overhead. Optimizations include reducing chunk count, choosing smaller embedding dimensions, quantization, compression, product quantization, disk-backed indexes, and tiered storage. These techniques trade memory for recall, latency, or precision. For example, quantization reduces memory but may slightly reduce nearest-neighbor accuracy. Evaluation is needed to ensure memory savings do not damage answer quality.
**Interview answer:** I would reduce duplicate chunks, consider smaller embeddings, use quantization or compression, and tier storage. Each optimization should be tested for recall and latency impact.

24. How would you design a RAG system that supports both batch analytics and interactive chat?
**Deep explanation:** Interactive chat needs low latency, permission enforcement, and conversational context. Batch analytics needs throughput, repeatability, and often larger context or structured outputs. A shared ingestion and indexing layer can serve both, but query execution should have separate queues, rate limits, model choices, and result storage. Batch jobs may use cheaper asynchronous processing, while chat requires fast timeouts. Mixing them without isolation can let large batch workloads harm interactive users.
**Interview answer:** I would share the indexed knowledge layer but separate serving paths, queues, rate limits, and model budgets. Chat gets low-latency priority, while batch jobs run asynchronously.

25. How would you approach capacity planning for RAG traffic?
**Deep explanation:** Capacity planning should estimate query volume, retrieval QPS, embedding calls, reranking load, model tokens, index size, update rate, and latency targets. The bottleneck may be vector search, model inference, external APIs, or ingestion throughput. Token usage matters because generation cost often dominates. Planning should use p95 and p99 latency, peak traffic, tenant distribution, and failure scenarios. Load testing with realistic query mixes is more useful than testing only average requests.
**Interview answer:** I would model traffic, tokens, retrieval load, update rate, and peak concurrency, then load test realistic query paths. Capacity should be planned around tail latency and bottleneck services.

26. How would you design a confidence score for RAG answers?
**Deep explanation:** A confidence score can combine retrieval signals, reranker scores, source authority, citation support, conflict detection, model self-checks, and historical performance for similar queries. It should not rely only on the LLM saying it is confident. Confidence should be calibrated against human-labeled outcomes so that, for example, 80 percent confidence roughly means 80 percent correctness. Poorly calibrated confidence is dangerous because users may overtrust precise-looking scores.
**Interview answer:** I would combine retrieval quality, source authority, citation support, conflict signals, and calibrated evaluation data. I would not trust model self-confidence alone.

27. How would you support blue-green deployments for RAG prompts and retrieval changes?
**Deep explanation:** RAG behavior depends on prompts, retrievers, rerankers, indexes, and model versions. Blue-green deployment lets a new configuration run beside the old one, then shifts traffic after validation. Shadow traffic can compare outputs without affecting users. The system should version prompt templates and retrieval configs so bad changes can be rolled back. Because answers are probabilistic, deployment checks should include quality metrics, latency, cost, and safety regressions.
**Interview answer:** I would version prompts and retrieval configs, run the new stack beside the old one, compare shadow or canary traffic, then shift gradually with rollback support.

28. How would you handle retrieval over codebases differently from retrieval over prose documents?
**Deep explanation:** Code retrieval benefits from syntax-aware chunking, symbol indexes, file paths, dependency graphs, commit history, and exact search. Embeddings help with conceptual queries, but exact identifiers and call relationships often matter more than prose similarity. Chunks should preserve functions, classes, imports, and nearby comments. Structured tools like language servers or static analyzers can improve retrieval. The trade-off is higher ingestion complexity but much better answers for implementation questions.
**Interview answer:** I would combine semantic search with symbol search, file metadata, dependency graphs, and syntax-aware chunks. Code RAG should preserve functions, classes, and exact identifiers.

29. How would you design human-in-the-loop review for high-risk RAG answers?
**Deep explanation:** Human-in-the-loop review is useful when wrong answers have legal, financial, medical, or operational consequences. The system can route answers for review based on confidence, topic, user role, source conflict, or action impact. Reviewers need the answer, retrieved evidence, citations, model trace, and suggested edits. The trade-off is latency, so high-risk workflows may be asynchronous or require approval before taking action. Reviewed examples can improve future evaluation sets.
**Interview answer:** I would route low-confidence or high-impact answers to reviewers with the supporting evidence and trace. Human review adds latency, but it is appropriate when mistakes are costly.

30. How would you design a RAG system that can answer from both historical documents and live operational data?
**Deep explanation:** Historical documents are well-suited to indexing, while live operational data often needs direct API or database access. A robust system routes the query to the right source: vector or keyword retrieval for stable documents, structured calls for current state, and synthesis when both are needed. It must label freshness clearly because indexed data may lag behind live systems. Access control should apply consistently across documents and live tools. The trade-off is orchestration complexity and more failure modes.
**Interview answer:** I would use indexed retrieval for stable historical knowledge and live APIs or databases for current operational facts. The answer should preserve provenance and make freshness clear.
